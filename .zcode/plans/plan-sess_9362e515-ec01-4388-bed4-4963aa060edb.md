# Plan : Réparation des notifications de rappels (Windows 11 + in-app + app fermée)

## Diagnostic (3 problèmes, 3 causes racines)

| Problème | Cause racine | Fichier |
|---|---|---|
| **Notif Windows cassées** | `_notify_windows()` utilise l'API legacy `Shell_NotifyIcon` (balloon tips), pas d'AUMID enregistré, process `--service` qui se termine après 2 s → Win11 supprime souvent le toast | `service.py:44-133` |
| **Rappels invisibles à l'ouverture** | `traiter_rappels_dus()` n'est jamais appelé au démarrage du sidecar FastAPI. La spec exige pourtant ce "filet de sécurité" (`spec.md:218-236`) | `server.py:1595-1618` |
| **Pas de toast in-app à l'ouverture** | `sonner` n'est utilisé que pour les feedbacks, jamais pour signaler les rappels dus | `App.tsx`, `main.tsx` |

## Décisions prises (confirmées par l'utilisateur)
- **Moteur notif Win** : PowerShell + `ToastNotificationManager` (vraies toasts Win11, AUMID, aucune nouvelle dépendance Python, fonctionne dans l'exe PyInstaller ET app fermée)
- **Comportement ouverture** : 1 toast résumé "Vous avez N rappels en attente" + badge de la cloche mis à jour

## Implémentation

### 1. Backend — Vrai toast Windows 11 via PowerShell (`apps/api/crm/service.py`)

Réécriture de `_notify_windows(title, message)` :
- Invoque `powershell.exe` via `subprocess.run` avec un script inline qui :
  - Crée une notification via `[Windows.UI.Notifications.ToastNotificationManager]` (WinRT)
  - Utilise un AUMID dédié `{tn.cabinet.gouiaaa.crm}` + nom d'app "Cabinet CRM" → les toasts s'affichent correctement dans le Centre de notifications Win11 et ne sont pas supprimés quand le process se termine
- **Fallback chaîne** : PowerShell toast → ancien code `win32gui` (gardé en 2e secours) → `plyer` (3e secours). Best-effort, ne lève jamais.
- Avantage clé : PowerShell est natif Win10/11, aucune nouvelle dépendance, fonctionne dans l'exe PyInstaller, et marche **app fermée** car c'est la tâche planifiée qui appelle `--service`.
- Mise à jour du docstring et des commentaires (style existant : français, explicatif).

### 2. Backend — Filet de sécurité au démarrage du sidecar (`apps/api/crm/server.py`)

Dans `_init_db()` (ligne 1595-1618), après `STATE.conn = conn` :
- Appel best-effort à `rappels_logic.traiter_rappels_dus(conn)` → les rappels en retard passent automatiquement `planifie` → `du`/`a_envoyer` à chaque ouverture de l'app, même si la tâche planifiée n'a pas tourné.
- **Pas d'émission de toast Windows ici** (le frontend gère le toast in-app au démarrage — éviter le double-toast).
- Wrapped dans `try/except` best-effort comme le reste de `_init_db`.

Cela satisfait le requirement *"Présentation des rappels dus au démarrage"* (`spec.md:218-236`) qui n'était **pas câblé**.

### 3. Frontend — Toast résumé à l'ouverture + refresh sur focus (`apps/web/src/`)

**3a. Nouveau hook `useRappelsStartup()`** dans `apps/web/src/hooks/rappels.ts` :
- Au mount, déclenche `traiter_rappels_dus` côté backend via un nouvel endpoint dédié (voir 3c), puis fetch `count-actifs`.
- Si `count > 0`, affiche un toast `sonner` : **"📅 Vous avez N rappel(s) en attente"** avec action "Voir" → `navigate('/rappels')`.
- Invalide `rappelKeys.countActifs` pour rafraîchir le badge immédiatement.

**3b. Rafraîchir la cloche au focus de la fenêtre** :
- Garder `refetchOnWindowFocus: false` globalement (ne pas casser la perf pour tout le monde), mais ajouter dans `RappelsBell.tsx` (ou un `useEffect` dédié) un listener `window.addEventListener('focus', ...)` + `visibilitychange` qui invalide `rappelKeys.countActifs`. Satisfait *"Rafraîchissement si l'app est déjà ouverte à l'échéance"* (`spec.md:231-236`).

**3c. Nouvel endpoint `POST /api/rappels/process-dus`** dans `apps/api/crm/routers/rappels.py` :
- Appelle `rappels_logic.traiter_rappels_dus(conn)` et renvoie `{ processed: N }`.
- Côté frontend, on appelle déjà ce traitement via `_init_db()` (filet backend), MAIS l'endpoint permet au frontend de le déclencher explicitement au mount (garantie fraîcheur, et utile en dev où le sidecar peut déjà tourner). Le rend idempotent grace à la nature de `traiter_rappels_dus`.

### 4. Tests + diagnostics

- **Mise à jour de l'endpoint test-notification** (`server.py:1535-1574`) : en plus du diagnostic actuel, journaliser quel chemin a réussi (PowerShell vs win32gui vs plyer) pour aider au débogage.
- Les fichiers de log existants (`data/logs/service.log`, `data/logs/notification_debug.txt`) captureront les succès/échecs.

## Ce qui n'est PAS dans ce plan (par design)
- **Pas de `tauri-plugin-notification`** : ne résout pas le besoin "app fermée" (ne marche que si l'app Tauri est ouverte). La tâche planifiée + service headless est la bonne architecture pour ce cas.
- **Pas de Web Push / service worker / PWA manifest** : non pertinent pour une app Tauri desktop.

## Vérification post-implémentation
1. Ouvrir l'app avec des rappels en retard → badge mis à jour + toast in-app résumé apparaît
2. Bouton "Tester la notification" (Paramétrage → Rappels) → vrai toast Win11 dans le Centre de notifications
3. Fermer l'app, créer un rappel échu en base, attendre la tâche planifiée (ou la déclencher) → toast Win11 apparaît app fermée
4. Vérifier `data/logs/service.log` et `notification_debug.txt` pour confirmer le chemin utilisé
